# П3.1.3 — подробная теория: телеметрия на RP2040

Этот конспект объясняет не общую физику электричества, а то, как измерительные и цифровые блоки RP2040 работают вместе, как прошивка обращается к ним и почему в проекте появляются отдельная задача, структура данных и указатель на функцию.

Материал относится к проекту `311-adc` и к заданию **«Телеметрия измерений»**. Внешний датчик или новая электрическая цепь в этой работе не добавляются: используются уже настроенные GP26, внутренний датчик температуры RP2040, системный таймер и USB CDC.

---

## 1. Что меняется по сравнению с п3.1.1 и п3.1.2

До этого компьютер сам инициировал каждое измерение: отправлял `get_voltage`, прибор измерял напряжение и отвечал. Это **опрос**: компьютер задаёт вопрос, прибор отвечает.

В п3.1.3 появляется **телеметрический поток**. Компьютер один раз запускает его, после чего прибор самостоятельно выдаёт записи с заданным периодом:

```text
Компьютер                 RP2040
   |                         |
   |---- tm_start 50 ------->|
   |<-- telemetry: started -|
   |                         | первое измерение
   |<---- tm: ... -----------|
   |                         | ожидание по системному времени
   |<---- tm: ... -----------|
   |                         | ожидание по системному времени
   |<---- tm: ... -----------|
   |                         |
   |---- tm_stop ----------->|
   |<-- telemetry: stopped -|
```

Команды:

| Команда | Результат |
|---|---|
| `tm_start` | Запустить поток с периодом по умолчанию 100 мс |
| `tm_start 50` | Запустить поток с периодом 50 мс |
| `tm_start 500` | Запустить поток с периодом 500 мс |
| `tm_stop` | Остановить поток |

Повторный `tm_start` перезапускает задачу с новым периодом. Минимально допустимый период — 10 мс.

Одна строка имеет формат:

```text
tm: <time_us> <voltage_v> <temp_c>
```

Например, `tm: 20933443 0.528 24.8`. Время указывается в микросекундах, напряжение — в вольтах с тремя знаками после точки, температура кристалла — в градусах Цельсия с одним знаком.

## 2. Внутри RP2040: аппаратные блоки и программные слои

RP2040 — это не только два вычислительных ядра Cortex-M0+. Внутри одного кристалла расположены память, контроллеры интерфейсов и специализированные аппаратные узлы: GPIO, ADC, TIMER, USB, UART, SPI, I²C и другие.

Упрощённо путь команды из программы к аппаратуре выглядит так:

```text
C-код
  ↓
функция Pico SDK
  ↓
чтение/запись регистра периферии
  ↓
внутренняя системная шина
  ↓
регистр и электрическая схема выбранного блока
```

**Регистр периферии** — ячейка по специальному адресу в адресном пространстве микроконтроллера. Запись определённых битов управляющего регистра может выбрать канал АЦП, включить датчик или настроить передачу. Чтение регистра результата позволяет получить то, что измерил аппаратный блок.

Нужно чётко разделять две операции:

- аппаратный блок физически выполняет операцию;
- процессор настраивает его, запускает действие и забирает результат.

Например, `adc_read()` не сравнивает программно аналоговое напряжение с тысячами уровней. Функция взаимодействует с отдельным аппаратным преобразователем.

В проекте слои разделены так:

| Слой | Обязанность | Примеры |
|---|---|---|
| Аппаратный RP2040 | Реально измеряет, считает время, передаёт USB-пакеты | ADC, TIMER, USB controller |
| `platform` | Скрывает детали конкретного микроконтроллера | `platform_voltage_read()` |
| `systime` | Даёт логике доступ к системному времени | `systime_us()` |
| `telemetry-task` | Решает, когда измерять и что включить в запись | `telemetry_task_handle()` |
| `api` | Обрабатывает команды и представляет запись в виде строки | `tm_start`, `api_print_telemetry()` |
| `main.c` | Связывает модули и вызывает их обработчики | суперцикл |

Поэтому `logic` не должна подключать `hardware/adc.h` или вызывать `adc_read()`. Она обращается к `platform`, а только `platform` знает, что под ним RP2040 и какой вызов SDK требуется. Это и есть разделение логики и аппаратной реализации.

## 3. Как формируется одна запись измерений

### 3.1. Один АЦП и несколько источников

У RP2040 один 12-разрядный SAR-АЦП. К нему через аналоговый мультиплексор подключаются разные источники:

| Канал | Источник |
|---:|---|
| 0 | GPIO26 (GP26) |
| 1 | GPIO27 (GP27) |
| 2 | GPIO28 (GP28) |
| 3 | GPIO29 (GP29) |
| 4 | Внутренний датчик температуры |

**Мультиплексор** — электронный переключатель. Он выбирает, какой сигнал подключить к общему входу АЦП. Он сам не измеряет и не преобразует напряжение.

Поэтому два значения снимаются последовательно:

```text
adc_select_input(0) → adc_read() → код GP26
adc_select_input(4) → adc_read() → код датчика температуры
```

Это не два независимых АЦП и не параллельное измерение. Между отсчётами проходит небольшое время. Для периодов 50–500 мс оно ничтожно мало, но с физической точки зрения измерения не одновременны.

### 3.2. Как работает SAR-АЦП на уровне блоков

SAR означает *Successive Approximation Register* — регистр последовательного приближения. Внутри АЦП есть схема выборки-хранения, внутренний ЦАП, компаратор и логика последовательного приближения.

Упрощённая последовательность преобразования:

1. Мультиплексор подключает выбранный аналоговый источник.
2. Схема выборки-хранения фиксирует входное напряжение на внутреннем конденсаторе.
3. SAR-логика устанавливает пробный старший бит кода.
4. Внутренний ЦАП формирует напряжение, соответствующее текущему пробному коду.
5. Компаратор сравнивает его с сохранённым входным сигналом.
6. SAR-логика оставляет или сбрасывает проверяемый бит.
7. Процесс повторяется для следующих разрядов.
8. Полученный 12-разрядный код становится доступен через регистр данных АЦП.

12 бит дают `2^12 = 4096` кодовых уровней, сами коды идут от 0 до 4095. Поэтому для упрощённого пересчёта применяется формула:

\[
U \approx K\frac{V_{REF}}{4096}.
\]

В `platform_voltage_read()` используется приближение `V_REF = 3.3 В`:

```c
adc_select_input(ADC_CHANNEL);
return (float)adc_read() * ADC_VREF_V / ADC_LEVELS;
```

Сначала выбирается канал 0, затем считывается код АЦП и масштабируется в вольты. Это приближённый расчёт: реальное опорное напряжение и шум влияют на результат.

### 3.3. Внутренний температурный датчик

Датчик температуры RP2040 — не цифровой датчик с готовым числом градусов. Это аналоговый чувствительный элемент внутри микросхемы, основанный на температурной зависимости напряжения перехода база–эмиттер транзисторной структуры.

Прошивка выбирает канал 4, считывает код АЦП, переводит его в напряжение и использует приближённую формулу:

\[
T = 27 - \frac{U - 0.706}{0.001721}.
\]

`U` выражено в вольтах, температура — в °C. Коэффициент `0.001721` В/°C соответствует приблизительному изменению напряжения на 1.721 мВ при изменении температуры на один градус.

Это температура **самого кристалла**, а не комнатного воздуха. На неё влияют собственный нагрев микросхемы, опорное напряжение и разброс параметров аналогового датчика. Это средство оценки температуры чипа, а не точный калиброванный термометр.

### 3.4. Почему структура объединяет не одновременные значения

```c
typedef struct
{
    uint64_t time_us;
    float voltage_v;
    float temp_c;
} telemetry_record_t;
```

Структура — один программный пакет взаимосвязанных данных. Она не означает, что все поля были измерены в один физический момент. В реализации временная метка снимается перед измерениями каналов GP26 и 4, то есть обозначает начало формирования набора.

## 4. TIMER: откуда берётся время

### 4.1. Зачем аппаратный таймер

Нельзя надёжно отмерять 50 мс количеством пустых циклов CPU: время такого цикла меняется в зависимости от частоты ядра, оптимизации компилятора и остальной нагрузки.

В RP2040 есть отдельный аппаратный TIMER с 64-разрядной шкалой времени в микросекундах. Счётчик изменяется аппаратно независимо от того, какой участок программы сейчас выполняет ядро.

Поэтому время продолжает идти, пока CPU принимает команду, выполняет расчёт, обновляет светодиод, считывает АЦП или отправляет USB-строку.

Pico SDK предоставляет функцию `time_us_64()`, а наша библиотека `systime` — оболочку:

```c
uint64_t systime_us(void)
{
    return time_us_64();
}
```

То есть `systime_us()` не получает часы компьютера и не считает выполненные инструкции. Она читает аппаратную шкалу времени микроконтроллера.

### 4.2. Почему 64 бита, если ядро 32-разрядное

Cortex-M0+ — 32-разрядное ядро, а TIMER предоставляет 64-разрядный счётчик. Такое значение можно прочитать несколькими 32-разрядными операциями. Но есть риск: если младшие 32 бита переполнятся между чтениями младшей и старшей частей, можно случайно собрать несовместимые части двух разных значений. Поэтому SDK применяет безопасное чтение с повторной проверкой старшей части.

Мы не обращаемся к регистрам TIMER самостоятельно: эту работу выполняет `time_us_64()`.

32-разрядный счётчик микросекунд переполнился бы примерно через 71.6 минуты. 64-разрядный диапазон позволяет практически не беспокоиться об этом.

### 4.3. Что именно означает time_us

`time_us` — монотонное время после начала системного отсчёта, а не календарная дата. Например, 21 000 000 означает примерно 21 секунду. Разность двух отметок показывает прошедшее между ними время.

## 5. Период и неблокирующий суперцикл

### 5.1. Суперцикл

В проекте нет отдельной операционной системы, создающей поток для каждой задачи. Есть один главный цикл — суперцикл. Он последовательно вызывает обработчики кнопки, светодиода, расчёта π и телеметрии.

Неблокирующая задача не ждёт наступления времени внутри себя. Она проверяет условие и быстро возвращается, если делать пока нечего. Поэтому `telemetry_task_handle()` вызывается на каждой итерации, но измерение происходит только тогда, когда наступил срок.

### 5.2. Перевод периода

В задаче хранятся:

```c
static uint64_t last_us;
static uint64_t period_us;
```

`last_us` — предыдущая контрольная точка, `period_us` — период в микросекундах. Например:

```c
period_us = (uint64_t)new_period_ms * 1000ULL;
```

Для 50 мс получится 50 000 мкс. Приведение к `uint64_t` выполняется до умножения, чтобы большое значение не переполнилось в 32-разрядной арифметике до помещения в 64-разрядную переменную.

### 5.3. Разбор `systime_period_elapsed()`

Упрощённо используемая функция имеет такой вид:

```c
bool systime_period_elapsed(uint64_t *last_us, uint64_t period_us)
{
    uint64_t now = systime_us();

    if (*last_us == 0) {
        *last_us = now;
        return false;
    }

    if (now - *last_us >= period_us) {
        *last_us += period_us;
        return true;
    }

    return false;
}
```

`uint64_t *last_us` — указатель: функция получает адрес переменной и может обновить её непосредственно. `*last_us` означает «значение по адресу last_us».

Условие `now - *last_us >= period_us` проверяет, прошёл ли заданный интервал. Если прошёл, функция прибавляет период к предыдущей контрольной отметке.

Почему не делает `*last_us = now`? Обработчик может быть вызван немного позже идеального времени. Если каждый раз начинать отсчёт от запоздавшего `now`, задержка будет накапливаться. Прибавление периода к старой отметке сохраняет базовую сетку времени. Небольшое отклонение реального времени от идеального называется **джиттером**.

Важный нюанс данной реализации: за один вызов функция прибавляет только один период. Если задача была задержана на несколько периодов, следующие быстрые вызовы могут несколько раз подряд вернуть `true`, пока контрольная точка не догонит текущее время. Не следует утверждать, что эта функция всегда пропускает все пропущенные интервалы.

### 5.4. Почему первый отсчёт делается сразу

По условию задания первый отсчёт должен появиться на ближайшей итерации после `tm_start`, а не после полного периода. Поэтому предусмотрен флаг:

```c
static bool first_record_pending;
```

Запуск устанавливает его в `true`. Ближайший вызов `telemetry_task_handle()` снимает первую запись сразу, запоминает её временную отметку как `last_us`, а последующие измерения разрешаются функцией `systime_period_elapsed()`.

Повторный `tm_start` сбрасывает расписание и тоже назначает немедленную первую запись.

## 6. Машина состояний IDLE / RUN

```c
typedef enum
{
    TELEMETRY_STATE_IDLE,
    TELEMETRY_STATE_RUN,
} telemetry_state_t;
```

Это простой конечный автомат:

```text
          tm_start
   IDLE -------------> RUN
    ^                   |
    |                   |
    +------ tm_stop ----+
```

В `IDLE` обработчик сразу возвращается и ничего не измеряет. В `RUN` он проверяет время и формирует запись, когда наступает нужный момент.

`switch` выбирает ветку по текущему состоянию. Переменные состояния объявлены на уровне файла с `static`: другие `.c`-файлы не могут изменить их напрямую. Они используют публичные функции `telemetry_task_start()`, `telemetry_task_stop()` и `telemetry_task_get_state()`. Это и есть инкапсуляция — внутренние данные скрыты за интерфейсом.

## 7. Структура, указатель и callback

### 7.1. Структура

Структура объединяет поля в один объект. Если объект обычный, поле читается через точку (`record.voltage_v`). Если есть указатель на структуру, используется стрелка (`record_ptr->voltage_v`). Выражение `p->x` эквивалентно `(*p).x`.

### 7.2. Указатель на функцию

Главная конструкция задания:

```c
typedef void (*telemetry_task_callback_t)
    (const telemetry_record_t *record);
```

Читаем по частям:

- `typedef` — создать новое имя типа;
- `void` — функция ничего не возвращает;
- `(*telemetry_task_callback_t)` — это указатель на функцию;
- аргумент `const telemetry_record_t *record` — функция принимает адрес записи;
- `const` — функция-получатель не должна менять поля записи через этот указатель.

Иными словами, переменная такого типа может хранить адрес функции с точно такой сигнатурой.

В `main.c` мы передаём адрес функции печати:

```c
telemetry_task_init(api_print_telemetry);
```

Задача сохраняет его:

```c
on_record = callback;
```

Когда измерение готово, выполняется:

```c
on_record(&record);
```

Фактически вызывается `api_print_telemetry(&record)`, но модуль телеметрии не обязан знать название этой функции.

Это называется **callback**, или обратный вызов: модуль получает указатель на чужую функцию и вызывает её позже, когда происходит нужное событие.

### 7.3. Почему указатель нельзя хранить навсегда

В `telemetry_task_handle()` запись объявляется как локальная переменная:

```c
telemetry_record_t record;
```

Она существует только во время текущего вызова функции. Callback вызывается синхронно, пока `record` ещё существует. Он должен прочитать и вывести данные сразу. Нельзя сохранить адрес `&record` и использовать его после возврата из функции: объект уже вышел из времени жизни.

`const` не продлевает время жизни объекта. Оно только запрещает изменять его через конкретный указатель.

### 7.4. Зачем нужен callback, если можно напрямую вызвать API

Прямой вызов `api_print_telemetry()` сделал бы модуль измерений зависимым от API. Тогда задачу нельзя было бы без изменения кода использовать для записи данных в буфер или передачи через другой интерфейс.

Callback инвертирует эту зависимость: задача знает только тип функции, а `main.c` связывает её с нужной реализацией.

## 8. Путь команды tm_start от компьютера до задачи

```text
USB CDC
  ↓
stdio / getchar
  ↓
stdio_text_protocol_handle()
  ↓
сбор строки и разбор на команду и аргументы
  ↓
api_handle()
  ↓
таблица api_commands[]
  ↓
cmd_tm_start()
  ↓
parse_u32() и проверка периода
  ↓
telemetry_task_start(50)
```

`stdio_text_protocol_handle()` собирает команду из входящих символов и возвращает структуру `command_t`, где находятся имя команды, количество аргументов и указатели на строки аргументов.

`api_handle()` ищет имя команды в таблице `api_commands[]` и вызывает соответствующую функцию-обработчик.

`cmd_tm_start()` проверяет синтаксис: не больше одного аргумента, аргумент состоит из десятичных цифр и помещается в `uint32_t`. После этого сама задача проверяет предметное ограничение — период не меньше 10 мс. Так API отвечает за корректность команды, а задача — за допустимость собственного режима.

## 9. Как printf доходит до USB CDC

`printf()` — функция форматированного вывода C. Сама по себе она не знает, что нужно отправить текст через USB.

В CMake включён USB stdio:

```cmake
pico_enable_stdio_usb(${PROJECT_NAME} 1)
pico_enable_stdio_uart(${PROJECT_NAME} 0)
```

А в `platform_init()` вызывается `stdio_init_all()`. Pico SDK связывает стандартный вывод с USB CDC (*Communication Device Class*). Компьютер представляет USB-устройство как виртуальный последовательный порт. Поэтому Windows показывает COM-порт, хотя это не отдельный аппаратный UART с линиями TX/RX.

Путь строки:

```text
api_print_telemetry()
  ↓
printf()
  ↓
stdio SDK
  ↓
USB CDC / TinyUSB
  ↓
USB-контроллер и PHY микроконтроллера
  ↓
линии D+ и D− кабеля
  ↓
USB host компьютера
  ↓
виртуальный COM-порт
  ↓
терминал или Python pyserial
```

Важное следствие: callback выполняется синхронно. Пока `api_print_telemetry()` выводит строку, `telemetry_task_handle()` не вернулась, а главный цикл не перешёл к следующей задаче. Поэтому вывод может вносить небольшую задержку и джиттер. Для периодов 50–500 мс и коротких строк это приемлемо. Для очень быстрых измерений применяют буферизацию, DMA, прерывания или отдельный механизм передачи — в п3.1.3 этого не требуется.

Формат печати:

```c
printf("tm: %llu %.3f %.1f\\n",
       (unsigned long long)record->time_us,
       (double)record->voltage_v,
       (double)record->temp_c);
```

`%llu` выводит `unsigned long long`; приведение времени обеспечивает соответствие формату. `%.3f` даёт три знака после точки, `%.1f` — один. Аргументы `float` в вызове вариадической функции автоматически продвигаются до `double`.

## 10. Профилирование обработчика

Для `telemetry_task_handle()` регистрируется отдельный секундомер `STOPWATCH_TELEMETRY` с именем `telemetry`:

```c
profiling_start(STOPWATCH_TELEMETRY);
telemetry_task_handle();
profiling_stop(STOPWATCH_TELEMETRY);
```

Профилировщик измеряет **длительность выполнения обработчика**, включая callback и печать, если в этой итерации была сформирована запись. Он не задаёт период между измерениями. Период задаёт `systime_period_elapsed()`.

## 12. Проверки перед защитой

1. `tm_start` запускает период 100 мс.
2. `tm_start 50` выдаёт записи примерно с шагом 50 000 мкс.
3. `tm_start 500` даёт около двух записей в секунду.
4. Повторный `tm_start` меняет период и начинает новый поток.
5. `tm_stop` прекращает новые вызовы callback.
6. `tm_start 5` отвечает `error: period_ms must be at least 10`.
7. `tm_start 10 20` и `tm_start 5x` отвечают `error: usage tm_start [<period_ms>]`.
8. После остановки `get_voltage` продолжает работать.
9. `device-3-1-3.log` содержит команды, ответы и телеметрические строки.

## 13. Вопросы преподавателя

**Почему задача не печатает сама?**  
Измерение и передача — разные обязанности. Задача формирует запись и вызывает callback; API отвечает за представление в виде строки.

**Почему callback, а не прямой вызов `api_print_telemetry()`?**  
Так `telemetry-task` не зависит от API и конкретного способа доставки данных.

**Почему передаём указатель на структуру?**  
Одна функция получает единый пакет всех измерений. Новое поле структуры не требует менять список аргументов функции.

**Что означает `const telemetry_record_t *`?**  
Это указатель на запись, которую нельзя изменять через этот указатель.

**Почему первая запись появляется сразу?**  
Флаг `first_record_pending` разрешает первый отсчёт на ближайшем вызове обработчика, не дожидаясь полного периода.

**Кто отсчитывает время, пока CPU занят?**  
Аппаратный TIMER — отдельный периферийный блок.

**Напряжение и температура измеряются одновременно?**  
Нет. Один АЦП поочерёдно подключает GP26 и канал внутреннего температурного датчика через мультиплексор.

**Останавливает ли `tm_stop` системный таймер?**  
Нет. Системное время нужно всем задачам. `tm_stop` переводит в `IDLE` только телеметрию.

**Зачем секундомер `telemetry`?**  
Он измеряет длительность обработчика, а не период измерений.
