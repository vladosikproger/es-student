# 3.2.1 — Индикатор записи

Проект `321-audio-recorder` создан на основе `311-adc`. В этом задании встроенный LED (GPIO25) переключается повторяющимся будильником SDK, а не задачей суперцикла.

## Команды

- `timer_blink_start <period_ms>` — запустить мигание, период переключения 10..60000 мс.
- `timer_blink_stop` — остановить мигание и вывести число переключений.

Пример проверки одновременной работы: `timer_blink_start 250`, затем `pi_start 3000000`, `uptime`, `pi`, `timer_blink_stop`.

Две кнопки GP15 и GP14, измерение напряжения и температуры, телеметрия и прежние команды сохранены. Во время таймерного мигания GPIO25 принадлежит callback таймера; для исключения конфликта задача LED переводится в состояние OFF.

## Сборка

Запускать из этой папки проекта:

```powershell
cmake -G Ninja -S . -B build
ninja -C build
```

Файл прошивки: `build\321_audio_recorder.uf2`.

```powershell
python check-3-2-1.py
```

Скрипт создаёт `device-3-2-1.log`.

## п3.2.2 — Захват по таймеру

Добавлен конечный захват отсчётов GP26 по повторяющемуся будильнику:

- `cap_start <N> <period_us>` — снять от 1 до 2000 отсчётов с периодом не менее 10 мкс;
- `cap_dump` — вывести коды АЦП, минимум/максимум фактических интервалов и долю времени внутри обработчика.

Во время захвата команды `get_voltage`, `get_temp` и `tm_start` отвечают `error: adc busy`; запустить захват во время телеметрии также нельзя.

Проверка и лог:

```powershell
python check-3-2-2.py
```

Скрипт создаёт `device-3-2-2.log`. Перед запуском закрой Serial Monitor, чтобы освободить COM-порт.


## п3.2.3 — Захват блока через DMA

Добавлен захват блока отсчётов GP26 без участия ядра в каждом измерении:

- АЦП работает в непрерывном режиме с частотой 44 100 Гц;
- FIFO АЦП формирует запрос `DREQ_ADC` для DMA;
- DMA переносит 16-битные значения из FIFO в `block_samples`;
- прерывание `DMA_IRQ_1` отмечает завершение блока;
- задача `block-task` передаёт готовый массив callback-функции в суперцикле;
- команда `dma_cap <N>` выводит фактическое и расчётное время, минимум, максимум и среднее значение отсчётов.

Новые внешние детали не требуются. Для этого задания GP26 оставляется свободным: значения АЦП будут плавать, поскольку мы проверяем прежде всего захват и временные характеристики.

Примеры команд:

```text
dma_cap 1000
dma_cap 4410
dma_cap 8192
```

Проверка и лог:

```powershell
python check-3-2-3.py
```

Скрипт создаёт `device-3-2-3.log`. Перед запуском закрой Serial Monitor, чтобы освободить COM-порт.

## п3.2.4 — Поток с двойной буферизацией

Добавлен непрерывный захват АЦП с двумя DMA-каналами и двумя буферами по 1024 байта:

- каналы DMA по цепочке поочерёдно заполняют буферы с частотой 44 100 Гц;
- `DMA_IRQ_0` отмечает заполненный буфер и возвращает адрес записи к его началу;
- задача `stream-task` формирует кадры с синхрословом `0x5aa5`, номером и числом отсчётов;
- `platform_write()` отправляет двоичные данные без преобразования `0x0a` в CRLF;
- `stream_start [16]` запускает поток и мигание GPIO25 с периодом 250 мс;
- `stream_stop` останавливает поток и выводит число кадров, отсчётов и переполнений;
- секундомер `stream` измеряет время отправки кадров.

На п3.2.4 аппаратная часть принимает только 16-битный режим (`stream_start` или `stream_start 16`). Аргумент 8 зарезервирован под последующее п3.2.7д.

## п3.2.5 — Запись испытательного сигнала

Добавлен генератор звукового испытательного сигнала на GP20 с помощью аппаратного PWM RP2040:

- счётчик PWM работает с частотой 1 MHz, то есть один тик равен 1 мкс;
- команда `generate_tone <Hz>` задаёт частоту меандра от 20 до 20 000 Гц;
- команда `generate_tone 0` устанавливает коэффициент заполнения 0 % и удерживает GP20 в LOW;
- логика API вызывает только интерфейс `platform_tone_set()` и не подключает заголовки Pico SDK;
- RP2040 применяет новые `TOP` и `CC` на границе периода, поэтому смена ноты не обрезает текущий импульс.

### Подключение

1. Полностью снимите RC-цепь из п3.1.5: и резистор, и конденсатор.
2. Соедините перемычкой физическую ножку 26 (GP20, PWM) с физической ножкой 31 (GP26, ADC0).
3. Не оставляйте конденсатор 100 мкФ на GP26: он сгладит меандр и создаст чрезмерную нагрузку на выход GP20.

### Проверка генератора

```text
dma_cap 1000
generate_tone 440
dma_cap 1000
generate_tone 0
```

При выключенном тоне отсчёты GP26 должны быть близки к нулю. При 440 Гц значения будут переключаться между нижней и верхней частями шкалы АЦП (примерно 0 и 4095), а среднее будет около половины шкалы.

### Запись испытательной мелодии

Закройте Serial Monitor. Скрипт `rec_audio.py` из п3.2.4 уже содержит таблицу нот и режим `--melody`:

```powershell
python rec_audio.py --wav melody.wav --melody
```

В результате рядом со скриптом появятся `melody.wav` и `melody.log`. Проверьте, что мелодия узнаваема, в логе нет пропущенных кадров, а в WAV один канал, PCM, 44 100 Гц и 16 бит. Эти два файла (`melody.wav` и `melody.log`) нужно отправить вместе с проектом.

## п3.2.6 — Сторожевой таймер

Добавлена защита от зависания суперцикла с помощью аппаратного watchdog RP2040:

- `platform_init()` самым первым действием определяет, был ли предыдущий сброс вызван watchdog;
- scratch-регистр 0 хранит число watchdog-сбросов подряд и переживает такой сброс;
- команда `wdt_enable <timeout_ms>` включает watchdog с таймаутом 1..8388 мс;
- `main.c` вызывает `platform_watchdog_feed()` только в конце полной итерации суперцикла, после всех задач;
- команда `hang` намеренно останавливает суперцикл, чтобы проверить автоматический перезапуск;
- команда `reset_reason` сообщает причину последнего сброса и число последовательных срабатываний watchdog.

### Почему watchdog обновляется именно в конце суперцикла

Признак исправной работы прибора — не просто работа ядра или приход прерываний, а успешное завершение всех задач очередной итерации. Если зависнет любая задача, выполнение не дойдёт до `platform_watchdog_feed()`, счётчик watchdog дойдёт до нуля и RP2040 перезапустится. Обработчики прерываний watchdog не обновляют.

### Выбор рабочего таймаута рекордера

Для рабочего режима рекордера выбран таймаут **8 мс**. По профилированию п3.2.4 худшая итерация во время потока занимает около 1,5 мс; 8 мс дают запас более чем в пять раз. При этом один буфер потока заполняется за 11,6 мс, поэтому таймаут остаётся короче времени заполнения буфера и ограничивает потерю данных при зависании. В испытании ниже используется 2000 мс, чтобы было удобно наблюдать перезапуск платы.

### Проверка на плате

Закрой Serial Monitor и из папки `321-audio-recorder` запусти:

```powershell

```

Скрипт проверит `reset_reason`, отклонение недопустимого таймаута 9000 мс, включение watchdog на 2000 мс, нормальную работу до истечения таймаута, намеренное зависание через `hang` и автоматическое переподключение к плате после перезапуска. Результат сохраняется в `device-3-2-6.log`.
