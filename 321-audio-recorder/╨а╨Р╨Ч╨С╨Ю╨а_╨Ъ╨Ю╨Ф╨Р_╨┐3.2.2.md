# п3.2.2 — разбор реализации по файлам

Реализация следует исходному заданию `п3.2.2 Захват по таймеру.md`. Имена команд, интерфейс `platform`, предел `PLATFORM_CAPTURE_MAX = 2000`, периодические вызовы `add_repeating_timer_us()` и формат ответа сохраняются по требованиям курса.

## 1. Что изменяется

| Файл | Изменение |

| `platform/platform.h` | интерфейс захвата, `platform_capture_t`, максимум 2000 отсчётов |

`CMakeLists.txt` не меняется: `hardware_adc` и `pico/time.h` уже используются предыдущими заданиями. `main.c`, `api.c`, библиотеки `libs/`, задачи кнопок и LED не переписываются.

## 2. `platform.h`

`PLATFORM_CAPTURE_MAX` ограничивает оба статических массива размером 2000 элементов. Интерфейс платформы возвращает `false`, если АЦП занят или параметры не позволяют запустить захват.

```c
#define PLATFORM_CAPTURE_MAX 2000
bool platform_adc_busy(void);
bool platform_capture_start(uint32_t count, uint32_t period_us);
bool platform_capture_done(void);

typedef struct {
    const uint16_t *samples;
    uint32_t count;
    uint32_t period_us;
    uint32_t min_interval_us;
    uint32_t max_interval_us;
    float handler_percent;
} platform_capture_t;

void platform_capture_get(platform_capture_t *capture);
```

`const uint16_t *samples` — указатель на готовый статический массив. Структура передаёт адрес, число и статистику, не копируя весь массив отсчётов.

## 3. `platform.c`

### 3.1. Владение АЦП

```c
typedef enum { ADC_FREE, ADC_CAPTURE } adc_user_t;
static volatile adc_user_t adc_user;
```

В момент захвата АЦП закреплён за callback. Это предотвращает одновременное переключение аналогового мультиплексора командами `get_voltage`/`get_temp` и телеметрией.

### 3.2. Буферы

```c
static uint16_t capture_samples[PLATFORM_CAPTURE_MAX];
static uint32_t capture_times[PLATFORM_CAPTURE_MAX];
```

Каждый код АЦП хранится в 16 битах, временная метка `time_us_32()` — в 32 битах. При 2000 элементах массивы занимают 4000 + 8000 = 12000 байт.

Массивы статические: в обработчике прерывания нельзя выделять память, а локальные массивы такого размера не следует размещать на стеке.

### 3.3. `on_capture()`

Порядок операций соответствует заданию:

1. запомнить начало callback через `time_us_32()`;
2. сохранить временную метку;
3. получить один код через `adc_read()`;
4. увеличить индекс;
5. прибавить длительность callback к общей сумме;
6. вернуть `true`, пока не набрано N значений;
7. после последнего отсчёта освободить АЦП и вернуть `false`, чтобы SDK снял повторяющийся будильник.

Внутри callback нет печати, ожиданий или выделения памяти.

### 3.4. Статистика

`platform_capture_get()` проходит по временным меткам и вычисляет разности соседних значений. Минимум и максимум этих разностей становятся `min_interval_us` и `max_interval_us`.

Доля обработчика рассчитывается так:

```text
handler_percent = 100 * sum(handler durations) / (last_time - first_time)
```

Измерение включает только тело `on_capture()`. Вход/выход IRQ и диспетчеризация SDK в эту оценку не входят, как отдельно оговорено в задании.

## 4. `api-callbacks.c`

### 4.1. `cap_start`

- ровно два целочисленных аргумента;
- N от 1 до 2000;
- period_us не меньше 10;
- запуск запрещён, когда работает телеметрия;
- если платформенный захват не запускается, выдаётся `error: adc busy`.

После успешной регистрации таймера команда отвечает сразу. Отсчёты накапливаются позднее в callback.

### 4.2. `cap_dump`

Требует завершённый захват. Сначала печатает сводную строку с N, заданным периодом, min..max фактических интервалов и долей обработчика. Затем печатает коды по 16 значений в строке с префиксом `cap:`.

### 4.3. Блокировка конкурирующих команд

Перед `get_voltage`, `get_temp` и `tm_start` проверяется `platform_adc_busy()`. При активном захвате команда отвечает ровно `error: adc busy` и не обращается к АЦП.

`cap_start` отдельно проверяет состояние телеметрии, потому что телеметрия также пользуется тем же аппаратным АЦП.

## 5. Проверка по порядку

1. Собрать и записать прошивку.
2. Закрыть Serial Monitor и запустить официальный `check-3-2-2.py`.
3. Изучить `device-3-2-2.log`, особенно две строки `capture:`.
4. Убедиться, что `cap_dump` вывел N кодов в диапазоне 0–4095.
5. Проверить GitHub Actions `3.2.2 Захват по таймеру`.

Примерные интервалы из задания — ориентир, а не точные константы: реальный разброс зависит от других прерываний и нагрузки USB.
