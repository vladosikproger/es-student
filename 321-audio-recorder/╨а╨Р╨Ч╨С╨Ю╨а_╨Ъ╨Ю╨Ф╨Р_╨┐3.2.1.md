# П3.2.1 — разбор реализации по файлам

## Общая задача

В этом задании новый проект `321-audio-recorder` наследует работающий `311-adc`. Пока мы не записываем звук: добавляем независимый от суперцикла индикатор будущей записи. Встроенный светодиод классической Raspberry Pi Pico подключён к GPIO25.

Цепочка исполнения:

`аппаратный счётчик TIMER -> сравнение будильника -> IRQ -> NVIC -> системный обработчик SDK -> callback on_blink() -> GPIO25`.

Важно: таймер сам не меняет вывод. Он формирует запрос; GPIO переключается коротким C-обработчиком.

## 1. `CMakeLists.txt` — новое имя проекта

Изменено только имя:

```cmake
project(321_audio_recorder)
```

CMake-имя использует подчёркивания, потому что это идентификатор сборки. Папка проекта при этом называется `321-audio-recorder`, а строка паспорта — `321-audio-recorder`.

Структура библиотек не изменилась. `platform` по-прежнему единственная библиотека проекта, которая линкуется с Pico SDK. `logic` не получает прямой зависимости от SDK: это важно для границы между аппаратной реализацией и логикой приложения.

## 2. `firmware.h` — паспорт прибора

```c
#define FIRMWARE_NAME    "es-recorder"
#define FIRMWARE_PROJECT "321-audio-recorder"
#define FIRMWARE_VERSION "1.0.0"
```

Команда `info` печатает эти константы. Они не меняют работу таймера, но позволяют отличить новый прибор от `es-adc`.

## 3. `platform/platform.h` — аппаратный интерфейс

Добавлены две функции:

```c
bool platform_blink_start(uint32_t period_ms);
uint32_t platform_blink_stop(void);
```

`uint32_t` — беззнаковое целое фиксированной ширины 32 бита. Период не бывает отрицательным на уровне команды; диапазон проверяется в платформенном модуле: 10..60000 мс.

`bool` сообщает, удалось ли запустить таймер. `platform_blink_stop()` возвращает число переключений.

Логика API знает только эти две функции. Она не должна знать про `repeating_timer_t`, IRQ или регистры RP2040.

## 4. `platform/platform.c` — аппаратный таймер и callback

Добавлен заголовок:

```c
#include "pico/time.h"
```

Он объявляет тип `repeating_timer_t` и функции `add_repeating_timer_ms()` / `cancel_repeating_timer()` из Pico SDK. `<stddef.h>` подключён ради стандартного `NULL`.

Состояние:

```c
static repeating_timer_t blink_timer;
static bool blink_running;
static volatile bool blink_on;
static volatile uint32_t blink_toggles;
```

- `blink_timer` хранит состояние таймера SDK. Он `static` и находится вне функций, потому что SDK будет обращаться к нему после возврата из `platform_blink_start()`.
- `blink_running` используется основным кодом для понимания, зарегистрирован ли таймер.
- `blink_on` меняется из callback, поэтому объявлен `volatile`.
- `blink_toggles` увеличивается в callback и читается после остановки, поэтому тоже `volatile`.

`volatile` запрещает компилятору считать, что значение обязательно остаётся неизменным между чтениями. Он **не** делает операции автоматически атомарными и не заменяет блокировки. В этом задании счётчик 32-битный, выровненный, изменяется только обработчиком, а читается после отмены таймера; поэтому отдельная критическая секция по условиям задания не нужна.

### Обработчик

```c
static bool on_blink(repeating_timer_t *timer)
{
    (void)timer;
    blink_on = !blink_on;
    gpio_put(LED_PIN, blink_on);
    blink_toggles++;
    return true;
}
```

Это callback, который SDK вызывает из контекста обработки прерывания пула будильников.

1. `(void)timer;` явно показывает, что параметр интерфейса нужен SDK, но в нашем обработчике не используется.
2. `!blink_on` инвертирует булево значение: `false` превращается в `true`, `true` — в `false`.
3. `gpio_put()` задаёт логический уровень GPIO25.
4. Счётчик увеличивается на один каждый раз, когда светодиод меняет состояние. Это именно число **переключений**, не полных циклов мигания.
5. `return true` говорит SDK сохранить повторяющийся таймер активным. `false` прекратило бы повторения.

Обработчик намеренно не использует `printf()`, `sleep_ms()`, `malloc()` или длинные циклы. Прерывание временно вытесняет основной код; долгий обработчик задержал бы суперцикл и другие IRQ.

### Запуск

```c
bool platform_blink_start(uint32_t period_ms)
{
    if (period_ms < 10U || period_ms > 60000U)
        return false;

    (void)platform_blink_stop();
    blink_toggles = 0;
    blink_on = false;

    blink_running = add_repeating_timer_ms(
        -(int32_t)period_ms, on_blink, NULL, &blink_timer);
    return blink_running;
}
```

- сначала диапазон 10..60000 мс;
- останавливается предыдущий таймер, чтобы второй запуск не создал второй параллельный источник переключений;
- счётчик обнуляется;
- отрицательный период означает start-to-start: следующая точка расписания считается от начала прошлого callback, а не от его завершения. Это предотвращает накопление длительности callback как дрейфа периода;
- `on_blink` — указатель на функцию, не вызов функции прямо сейчас;
- `NULL` означает отсутствие дополнительных пользовательских данных;
- `&blink_timer` передаёт SDK адрес долгоживущей структуры состояния.

### Остановка

```c
uint32_t platform_blink_stop(void)
{
    if (blink_running) {
        (void)cancel_repeating_timer(&blink_timer);
        blink_running = false;
    }
    blink_on = false;
    gpio_put(LED_PIN, 0);
    return blink_toggles;
}
```

Отменяет повторяющийся будильник, переводит внутреннее состояние в OFF, физически гасит GPIO25 и возвращает количество переключений.

## 5. `logic/api/api-callbacks.c` — команды пользователя

Существующая `parse_u32()` проверяет, что аргумент состоит только из десятичных цифр и помещается в `uint32_t`. Мы используем её, не пишем второй парсер.

### `timer_blink_start`

Обработчик проверяет, что передан ровно один корректный аргумент. Затем вызывает `platform_blink_start(period_ms)`.

Если аргумент неверен:

`error: usage timer_blink_start <period_ms>`

Если платформа не приняла значение:

`error: period_ms must be 10..60000`

После успешной регистрации таймера выполняется:

```c
led_task_set_state(LED_STATE_OFF);
```

Почему это необходимо? До задания GPIO25 переключала обычная `led_task_handle()` в суперцикле. Теперь GPIO25 меняет таймерный callback. Если оба механизма останутся активными, они начнут перезаписывать состояние одного вывода. `LED_STATE_OFF` заставляет обычную LED-задачу больше не менять GPIO.

Затем печатается подтверждение запуска.

### `timer_blink_stop`

Вызывает `platform_blink_stop()`, получает число переключений и печатает:

`timer_blink: stopped, N toggles`

Печать выполняется в обычном API-коде, а не внутри обработчика прерывания.

Обе команды добавлены в `api_commands[]`. Именно эта таблица используется командным API для поиска обработчика по имени.

## 6. Что не изменялось

- `main.c`: суперцикл продолжает выполнять команды, LED-task, две кнопки, расчёт π и телеметрию.
- `led-task.c`: обычная логика LED остаётся на месте; на время таймерного мигания она переводится в OFF.
- `button-task.c`: кнопки GP15 и GP14 сохранены.
- АЦП, измерение напряжения и температуры, телеметрия и расчёт π не удалены.
- `logic` не линкуется напрямую с Pico SDK.

Кнопки сохранены физически и программно. Пока таймерный callback владеет GPIO25, кнопки лучше не нажимать: их обычные LED-действия тоже меняют GPIO25. После `timer_blink_stop` обычное управление LED кнопками снова доступно.

## 7. Проверочная последовательность

```text
help
timer_blink_start 250
pi_start 3000000
uptime
info
pi
timer_blink_stop
timer_blink_start 100
timer_blink_stop
timer_blink_start 5
timer_blink_start
```

При `timer_blink_start 250` состояние переключается 4 раза в секунду, то есть получается 2 полных цикла мигания в секунду. Счётчик в ответе `stop` считает переключения, а не полные циклы.

Ошибочные команды должны дать:

```text
error: period_ms must be 10..60000
error: usage timer_blink_start <period_ms>
```
